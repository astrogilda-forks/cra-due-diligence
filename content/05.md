# How open source projects and stewards can help manufacturers to achieve due diligence

- Voluntary attestation
- Provide security history
- Maintain security process description and evidence it is followed

## Test data for integration testing

A project cannot test an integration it has never seen. It can ship what an integrator needs to test the component inside the integrator's own product. The core of it is a set of test vectors, each pairing an input with the result the component should return. The reject cases carry the most weight, since that is where independent implementations tend to disagree.

A manifest pins the component revision and the vector revision together, so any result traces back to both. A runner, a script or CI step in the integrator's build, re-runs the vectors on each update and names the vector whose result changed. The project can also state the type and level of testing it performs, which the integrator can cite in the manufacturer's own assessment.

Each run's outcome belongs in the due diligence record described in chapter 3. It is one checked property, with the test output referenced by its cryptographic digest.

For example, [agent-evidence-vectors](https://github.com/probityai/agent-evidence-vectors) publishes its vectors with a manifest and a GitHub Action. A dependent project adds one step to its CI, and the build fails when a result changes.
