# How open source projects and stewards can help manufacturers to achieve due diligence

- Voluntary attestation
- Provide security history
- Maintain security process description and evidence it is followed

## Test data for integration testing

Article 13(5) of the CRA requires a manufacturer to exercise due diligence on the components it integrates, and Recital 34 lists the actions that satisfy it: checking for the CE marking, checking the security update history, checking the vulnerability databases, or "carrying out additional security tests". A free and open-source component that was not made available on the market in the course of a commercial activity carries no CE marking, so the security tests are the main evidence for it. A project cannot test an integration it has never seen. It can ship what an integrator needs to run those tests inside the integrator's own product.

The core of it is a set of test vectors, each pairing an input with the result the component should return. Reject cases matter most. That is where independent implementations tend to disagree.

A manifest pins the component revision and the vector revision together, so any result traces back to both. A runner, a script or CI step in the integrator's build, re-runs the vectors on each update and names the vector whose result changed. When the project fixes a vulnerability, it adds a vector that reproduces it, and the integrator's next run shows whether the fix holds in their own build.

An integration guide states what the component needs from its operating environment: the security functions it relies on the product to provide, and the configurations it does not support. Where an assumption can be tested, the project ships a test with the guide. A library that relies on the operating system for randomness, for instance, can ship a check that fails when no secure source is available, and the integrator runs it where the component is deployed. The project can also state the type and level of testing it performs, which the integrator can cite in the manufacturer's own assessment.

Each run's outcome belongs in the due diligence record described in chapter 3. It is one checked property, with the test output referenced by its cryptographic digest.

For example, [agent-evidence-vectors](https://github.com/probityai/agent-evidence-vectors) publishes its vectors with a manifest and a GitHub Action. A dependent project adds one step to its CI, pinned to a release tag, and the build fails when a result changes.
